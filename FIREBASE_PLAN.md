# План: что ещё взять из Firebase

Обсуждено 24 ноября 2026. Сделано: пуш о релизе (FCM, тема `releases`, `scripts/notify-release.mjs`) и отчёты о сбоях
(Crashlytics). Проект Firebase — `budgetapp-eced3`; `android/app/google-services.json` в репозиторий не кладётся
(репозиторий публичный), CI берёт его из секрета `GOOGLE_SERVICES_JSON`. Новая библиотека Firebase — та же BoM
(`firebase-bom:32.7.0` в `android/app/build.gradle`), без `@react-native-firebase`: нативный модуль на Kotlin + обёртка
в `src/native/`, как `crash/` и `update/`. Сборка без `google-services.json` должна собираться и работать без Firebase.

Каждый пункт — отдельный коммит (по «пуш»), после — скилл `finish`.

## 1. Remote Config — шаблоны SMS банка без нового релиза

**Зачем.** TBC меняет формат SMS или пуша — сейчас нужен релиз, и до обновления операции не распознаются (копятся в
«Не распознано»). С Remote Config шаблоны правятся в консоли, телефон подхватывает при следующем запуске.

**Как.**
- Вынести из парсера (`src/parsers/`) то, что меняется у банка, в данные: регулярки суммы/валюты/мерчанта/баланса,
  отправители, признаки типа операции. Парсер читает их из настройки; по умолчанию — зашитые в код (как сейчас).
- Нативный модуль `config/RemoteConfigModule.kt`: `fetchAndActivate` при запуске (не чаще раза в час), отдаёт JSON
  шаблонов в JS; JS кладёт в `app_settings`, чтобы headless-задача SMS видела их без сети.
- Проверка шаблонов перед применением: прогон на SMS из `tests/logic/` (fixtures) — сломанный шаблон не применяется,
  остаются прежние (и ошибка — в Crashlytics).
- Тесты: парсер с шаблонами из данных = парсер из кода на всех fixtures.

**Риск.** Удалённые шаблоны — удалённое управление разбором денег: только регулярки, никакого кода; версия схемы
шаблонов, чтобы старое приложение не взяло несовместимые.

## 2. Резервная копия в облаке — автоматически и зашифрованно

**Зачем.** Автокопия раз в неделю пишет файл на телефон (или в выбранную папку): потерялся телефон — копия с ним.

**Как.**
- Firebase Storage + Authentication (анонимный вход или Google): файл `users/{uid}/backup-YYYY-MM-DD.enc`; правила
  Storage — доступ только своему `uid`.
- Шифрование на телефоне до отправки тем же паролем, что у зашифрованной копии сейчас (`backup/`); Google видит только
  зашифрованный файл. Без пароля облачную копию не включать.
- В «Настройки → Приложение → Резервная копия»: свитч «Копия в облаке» (последняя — дата), «Восстановить из облака»
  на новом телефоне (вход тем же аккаунтом — анонимный вход для этого не годится, нужен Google).
- Хранить последние 4 копии; бесплатный лимит Storage — 5 ГБ.

**Решить до начала.** Вход через Google (переносится на новый телефон) или анонимный (проще, но восстановить на
другом телефоне нельзя).

## 3. Test Lab — прогон на настоящих телефонах

**Зачем.** Maestro идёт только на эмуляторе Pixel; MIUI/HyperOS (установка обновления, задержка пушей, фоновые задачи)
ловится только на живом Xiaomi.

**Как.**
- Robo-тест (без своих сценариев) или Maestro через Test Lab (`gcloud firebase test android run`) на 1–2 моделях
  Xiaomi и одном Samsung — вручную перед заметными релизами (workflow `workflow_dispatch`), не на каждый пуш:
  бесплатно — несколько прогонов в день.
- Нужен сервисный аккаунт с ролью Test Lab (можно тот же `FIREBASE_SERVICE_ACCOUNT` с добавленной ролью).

## Не делаем

- **Analytics** — отправлял бы в Google, как пользуются приложением; для личного бюджета пользы мало.
- **App Distribution** — своя доставка обновлений (GitHub-релиз + пуш + `PackageInstaller`) уже есть.
- **Firestore для операций** — данные перестали бы жить только на телефоне.
